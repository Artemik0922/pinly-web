# Производительность: что держит цифры

Метод замера: Lighthouse-трейс из DevTools и повторяемый прогон Playwright — LCP
и CLS по 4–5 заходам, потому что с одного замера доверия им нет. С 2026-11-06
метод собран в команду: `npm run build && npm start && npm run perf:report`
(Pixel 7, CPU×4, медиана из `RUNS` замеров, пороги LCP 2.5 с и CLS 0.1; падает
на нарушении, как `ui:audit`).

| Метрика | Было | Стало |
| --- | --- | --- |
| LCP главной (десктоп, без троттлинга) | 867 мс | **288 мс** |
| CLS | сетка скакала на загрузке картинок | **0.00** |
| 20 карточек первого экрана | растровые оригиналы | **≈144 КБ AVIF** |
| TTFB страницы категории (прогретый прод) | — | **≈44 мс** |

Ниже — то, что неочевидно из кода и что легко сломать обратно.

## Карточки не прячутся до загрузки картинки

Место резервируется `aspect-ratio` коробки, поэтому сетка не пересобирается
пачкой. Прежний `display:none` с опросом каждые 150 мс давал reflow на ~55 мс,
полсотни висящих узлов и держал LCP на 500 мс дольше.

## `connection()` вызывается в корне страницы, а не под `Suspense`

Иначе отдаётся статическая оболочка, а лента догоняет отдельным запросом после
гидрации: картинки стартуют на ~450 мс позже, чем могли бы, и краулер видит
страницу без пинов. Это же ловит и `instant = false` на страницах с серверными
данными — подробный разбор в [seo-and-analytics.md](seo-and-analytics.md).

## Приоритет только у первых 4 карточек

`fetchPriority="high"` + eager. Больше — хуже: с 10 приоритетными картинками LCP
вырос со 156 мс до 292, они вытесняют друг друга с одного канала.
`column-fill: balance` в CSS-колонках означает, что порядок в DOM ≠ порядок на
экране, поэтому запас в 4 карточки сознательный, а не точный.

## Картинки идут через `next/image` в AVIF/WebP

С ограниченным набором ширин: 100..7000 с шагом выносило бы в кэш отдельную
копию на каждый размер. Моки ленты — исключение, они грузятся с внешнего хоста
напрямую, потому что оптимизатор до `images.weserv.nl` не достучится.

## Носители пина

- **`preload="none"` у видео в карточке.** В ленте грузится только активный
  слайд: замер показал 2 МБ за 220 мс на играющем ролике и 0 байт на двух
  соседних карточках с видео. Иначе экран ленты = несколько роликов на одном
  канале.
- **Файл пишется на диск частями.** Видео до 60 МБ не должно ложиться в память
  единственного воркера целиком.
- **Раздача с `Accept-Ranges`.** Без диапазонов Safari не играет ролик вовсе, а
  Chrome перекачивает файл целиком на каждый шаг ползунка.
- **Постер вместо видеокадра в обложке.** `og:image`, превью доски и сетка
  остаются обычными картинками и не платят за видео.

## Замер 2026-11-06: самый тяжёлый файл сайта — его же логотип

Знак в шапке и на заставке жил в `public/logo-mark.png` как 512×512 RGBA на
186 КБ и ехал на каждую страницу как есть, с `Cache-Control: max-age=0`. На
экране это 36 px в шапке и 64 px на заставке. Теперь он проходит через
`next/image` (локальный путь добавлен в `images.localPatterns`): 3 927 байт
AVIF на w=192 и обычные для `/_next/image` `immutable`-кеширование.

| Что | Было | Стало |
| --- | --- | --- |
| logo-mark одной страницы | 186 557 байт PNG | **3 927 байт AVIF** |
| кандидатов в `srcset` | 17 (96…1920) | **12 (96…1536)** |
| HTML страницы категории | 204.8 КБ | **182.9 КБ** |
| первый визит, лента (Pixel 7 + CPU×4) | 674 КБ | **493 КБ** |
| LCP ленты | 1836 мс | 1828 мс — **не изменился** |
| LCP поиска | 276 мс | **260 мс** |

Три честные заметки к таблице.

**LCP ленты не улучшился, и это результат, а не промах.** Замер говорит, что
самым крупным элементом там является картинка ленты (`img.w-full`, 49.6 КБ), а
она приезжает в стриминговой части страницы; логотип на неё не влиял. Логотип и
есть LCP там, где показывается заставка — на поиске это теперь `img.splash-logo`
в 4 КБ вместо 186-килобайтного PNG, и ему добавлен `priority`.

**Лестница ширин не сокращалась `sizes`.** Для внешних (unoptimized) картинок
Next кладёт в `srcset` все ширины из конфига, а моки ленты едут именно так: 17
кандидатов по ~540 байт (URL weserv двойным кодированием) — 9.2 КБ HTML на одну
карточку, и столько же в каждом `<link rel=preload>`. 12 значений — это потолок
того, что сайт рисует: карточка ленты при DPR 2 — ~730 px, крупный носитель на
странице пина — ~1536 px.

**`/pin/<id>` с LCP 19.7 с — это не сайт.** В локальном прогоне моки тянутся
браузером напрямую с `images.weserv.nl`, и с этой машины он отвечает за 19–67 с;
в отчёте это строка «тормоз» под маршрутом. Прод-контент идёт через `/api/img`,
но и там холодный кэш источника остаётся единственным, что способно затормозить
сайт заметно (см. ниже и `npm run warm`).

## Прочее

- Моноширинный веб-шрифт удалён: класс не использовался ни в одном компоненте,
  а запрос и ~20 КБ были.
- На CPU×4 прогретая страница держит 200–500 мс. Холодный кэш источников —
  единственное, что способно затормозить сайт заметно, и для этого есть
  `npm run warm`.
